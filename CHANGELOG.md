# Changelog

All notable changes to the DELTA Windows Docker Installer will be documented in this file.

## [Unreleased]

### Added

- Long-running operations now show an animated activity indicator instead of a still screen. An operation that has started and is being waited on prints `Installing Docker Desktop.` / `..` / `...` cycling on one line, and that line is erased when the operation ends — so what is left in the scrollback, and in the transcript, is exactly what was there before. It is a generic mechanism (`Invoke-DeltaActivity -Message … -ScriptBlock { … }`) rather than a list of blessed operations: any future operation can use it without changing the indicator. There are no percentages and no estimated completion times, because this installer cannot know either. Animation is presentation only — the transcript records one line per operation, never a frame — and it is turned off automatically when output is redirected, when the session is not interactive, when the host is not a console, when the line would not fit the window, and for `-NonInteractive`, where a single static `Installing Docker Desktop...` is printed instead. Nothing animates while a prompt is waiting for an answer.
- The activity line now carries a spinner and an elapsed counter: `    \ Starting DELTA (1m 14s)`. The three-dot cycle said something was happening but not for how long, which is the one number an operator actually wants during a nine-minute image pull. Seconds up to a minute, then `m ss`. The clock belongs to the operation, not to the line, so an operation interrupted by a status line comes back reading the time it has really been running rather than restarting at zero. The spinner frames are chosen from the console's output encoding — braille on UTF-8, ASCII `-\|/` on a legacy code page — because a glyph the console cannot represent is a question mark redrawn eight times a second. One renderer produces the line, compiled from a single source string in both the main thread and the animation runspace, so the two can never disagree by a character.
- The static fallback is unchanged and deliberately carries neither: `    Starting DELTA stack...`, once, no clock, no spinner. A transcript still records the sentence exactly once and never a frame or a counter.
- Coverage completed after an audit of every blocking call in the installer and the management utility. Newly animated: the OpenSSL container that validates a supplied certificate/key pair and the one that generates a self-signed certificate (the first certificate operation of an installation may pull that image); `docker info`, which is the probe every Docker decision rests on and which takes its full two-minute budget to report a wedged engine; `wsl --status` / `--version`, instant until WSL is half-installed; `compose ps`, which is what the management screen sits on while it refreshes and the first thing to touch a cold engine; `compose config` and the JSON model render; the A§9.4 database-volume precheck, which starts a container before every start; and the NGINX access-log rotation's `mv` and `nginx -s reopen`. The shared primitives are marked `-WhenIdle`, so they animate when reached on their own and stay silent inside an operation that already says what it is waiting for.
- Migrated to the indicator: the Docker Desktop download and silent install, enabling the Virtual Machine Platform feature, the WSL platform install, starting Docker Desktop and switching it to Linux containers, the image pull, starting each of the three containers, the database backup, the update's pull and container recreation, and the uninstall's archive creation and verification.
- The indicator covers a whole logical operation rather than one subprocess inside it, and every wait the installer performs is one. `==> Starting DELTA` used to animate for the second or two `docker compose up -d delta` takes to create the container, then stop — leaving the terminal still for the ninety seconds of cold start the step had just warned about, because the waiting is done by the health poll after it. It now animates from the moment the step begins until DELTA is healthy or has failed, and the same is true of the database and NGINX starts, the Docker engine wait, the update's health wait, and the certificate flow's. A polling loop's own status line — `Waiting for delta (15 s; state running, health starting)` — is written as it always was; it suspends the line, prints, and the line comes straight back, so the other fourteen seconds no longer look like a stopped installer. Also newly covered: the database version and extension queries, the initialisation verification, the HTTP endpoint check, the registry digest query, the administrator password apply and verify, the NGINX configuration test and reload, `compose stop`, and the uninstall's survey, `compose down`, volume removal and directory delete.
- Operations nest. An inner operation takes the line over and hands it back when it finishes, so completing one can never leave an outer operation that is still in progress looking finished; at most one line is ever animated, at any depth. Operations that are usually part of something larger — the shared waits, queries and teardown primitives — announce themselves only when they are reached on their own (`-WhenIdle`), so a nested one adds neither a second line to the terminal nor a second line to the transcript.
- Prompts now suspend the indicator rather than ending it, so a question asked from inside an operation is answered and the operation carries on saying that it is running. Nothing animates while a prompt or a modal dialog is waiting, and suspensions are counted, so a question whose own text is written through the output helpers cannot bring the animation back while it is still on screen. The two live log viewers suspend it for the same reason and restore it on the way out.

### Fixed

- **The two bind-mounted log directories now get an ACL of their own, and NGINX log rotation works on a host where the installing account is an ordinary administrator.** `logs\delta` and `logs\nginx` were created with `New-Item` and nothing else, so each inherited the installation root's entries. Measured on a real installation, every log file the containers had already written carried `BUILTIN\Users:(I)(RX)`, owned by `BUILTIN\Administrators`, with **no entry at all for the account Docker Desktop runs as** — `CREATOR OWNER` materialises from whichever token performed the write. So any local interactive account could read the NGINX access log, which is a record of who requested what, and DELTA's application log with it; and whether the installer could rotate anything depended on that account's token still carrying `BUILTIN\Administrators` enabled, which a UAC-filtered administrator token does not. Both directories are now given, on every run: Administrators and SYSTEM inheritable full control, and the single account Docker Desktop reads and writes host files as **Modify**, inheritable. Every broad principal goes, explicitly as well as by inheritance. `logs\installer` is deliberately not included — nothing is mounted there.
- **Modify for both, measured per directory rather than assumed, and they fail the cheaper grant differently.** `logs\delta` was driven through the DELTA image's *own* `winston` + `winston-daily-rotate-file` transport with the options the application builds: with `<user>:(RX,W)` logging works and then `rename` and `delete` fail, leaving 26 rotated files and the audit file behind — retention silently dead, which is the disk-fill this installation already has a scheduled task to prevent. `logs\nginx` was driven through the real `Invoke-DeltaNginxLogRotation` against a real NGINX container: with `(RX,W)` NGINX starts and logs, and then *every* rotation fails with `mv: can't rename '/var/log/nginx/access.log': Permission denied`. NGINX never renames anything itself — the rename is the installer's own rotation, issued **inside** the container so the file NGINX holds open moves with POSIX semantics, which means it crosses the 9p link as the Docker Desktop account and needs `DELETE` on the Windows side. Windows `W` does not carry `DELETE`; Modify does. Not Full Control: no container changes an ACL or an owner, so `WRITE_DAC` and `WRITE_OWNER` are exactly what it would add for nothing.
- The two ACLs that fail outright are pinned as regressions rather than described. `Administrators + SYSTEM` refuses the DELTA mount at `docker: Error response from daemon: Access is denied` and refuses to create the NGINX container at all. A `Program Files` style root — `BUILTIN\Users:(RX)` and no add — kills the DELTA logger with `Error: EACCES: permission denied, open '/delta/logs/dts-<date>.log'` raised as an **unhandled** `error` event, so the Node process exits, and stops NGINX before it serves anything with `nginx: [alert] could not open error log file: open() "/var/log/nginx/error.log" failed (13: Permission denied)`. The installer's own writability probe runs elevated and would not have caught either.
- Ownership is deliberately left alone. The directories and the files the containers create are owned by `BUILTIN\Administrators` on a Windows Server host and by the user account on a filtered-token host, and under this ACL neither matters: all three entries are explicit and inheritable, so effective access is identical either way. Taking ownership would change a displayed value and no behaviour, on files an operator may have put there themselves.
- The host-side half of rotation needed no second principal. The retention delete always runs on Windows, and the rename does too when NGINX is stopped — both from the daily task, which is registered S4U as the installing account at `RunLevel Highest`, so it is covered twice: by that account's own Modify entry and by Administrators. Existing installations are repaired on rerun without a log being created, moved, truncated or deleted; logs already on disk keep their content and re-inherit the new entries, which is what makes rotation start working on an installation where it never could.
- **`uploads\` now gets an ACL of its own instead of whatever the installation root happened to inherit.** It was created with `New-Item` and nothing else, so on the default `C:\DELTA` it carried the root-of-`C:` defaults — measured: `BUILTIN\Users:(OI)(CI)(RX)` plus `(CI)(AD)` and `(CI)(WD)`, and `CREATOR OWNER:(OI)(CI)(IO)(F)`. That is both too broad and not stable. Too broad, because every file DELTA writes lands with `BUILTIN\Users:(RX)` on it: every local interactive account could read every uploaded document, and any of them could plant files and subdirectories in the tree. Not stable, because those `Users` entries are a property of the *drive root*, not of this installation — and the installer offers a folder picker. Measured against a real engine on DACLs written as a UAC-filtered administrator token evaluates them, a `Program Files` style root (`Users:(RX)`, `CREATOR OWNER`, `SYSTEM`) projects into the container as mode `555` and *every* write fails, while an `Administrators + SYSTEM` root fails earlier still, at `docker: Error response from daemon: Access is denied`, before the mount is established. Worse, a file the container itself creates carries no entry at all for the account Docker Desktop runs as — `CREATOR OWNER` materialises from whichever token performed the write, measured as `BUILTIN\Administrators` on a Windows Server host — so whether an existing upload stays writable depended on that account's token still carrying `BUILTIN\Administrators` enabled. `uploads\` is now given, on every run: Administrators and SYSTEM inheritable full control, and the single account Docker Desktop reads and writes host files as **Modify**, inheritable. Every broad principal goes, explicitly as well as by inheritance.
- **Modify, and not less, because DELTA's own file operations set the floor.** Its server bundle moves each upload out of `uploads/<tenant>/temp` with `fs.renameSync`, deletes with `fs.unlinkSync`, and drops a whole tenant tree with `fs.rmSync(recursive: true)`. Measured on the real bind mount with the real image: the `(RX,W)` grant the certificate staging directory uses — the obvious thing to reuse — fails `rename`, rename across directories, directory rename and recursive delete, because Windows `W` does not carry `DELETE`. `(M)` passes the whole matrix. Not Full Control: that would add `WRITE_DAC` and `WRITE_OWNER`, and nothing in the application changes an ACL or an owner. `(OI)(CI)` on all three entries, so uploads and tenant directories created later inherit the same rights rather than becoming unusable the moment they are written.
- Existing uploads are never touched. The ACL is applied to the directory that is already there — nothing is deleted, moved or recreated to repair permissions — and children re-inherit the new entries because their own inheritance is left alone. A rerun repairs a broken ACL rather than accumulating entries, and the uninstall backup still walks `uploads\` through Administrators. When there is no user account to grant — the installer running as SYSTEM — nothing is changed at all, because what would be left is precisely the `Administrators + SYSTEM` ACL measured to break the mount. `.env`, the certificates, the database volume and every other path are unchanged.
- **The certificate-management staging directory is now actually hardened, and stays usable by Docker.** `New-DeltaCertificateStaging` creates `certs\.staging-<guid>`, puts a private key through it, and hands it to `Protect-DeltaSecretFile` — whose first line returns for anything that is not a leaf. A directory is not a leaf, so the call had always returned without touching the ACL, and the directory kept `certs\`'s inherited entries including `BUILTIN\Users:(RX)`: any local user could read a private key for the length of a certificate operation, in the one place the code most believed it was protected. The trap was that the obvious repair breaks Windows 11 — this directory is bind-mounted into a container that *writes* the generated certificate and key into it, and measured against a real engine on a DACL modelling a UAC-filtered administrator token, `Administrators:(F) + SYSTEM:(F)` fails at `docker: Error response from daemon: Access is denied` before the mount is even established. A new `Protect-DeltaSecretDirectory` handles directories properly: Administrators and SYSTEM keep inheritable full control, every broad principal goes, and the one account Docker Desktop reads and writes host files as gets **read/execute and write**, inheritable. Not Read — measured, the container then fails with `cannot create /work/openssl.err: Permission denied`, so the deployed key's grant could not be reused here. Not Modify or Full Control — the workflow only creates files, and the directory is removed afterwards by the host through Administrators. The deployed `delta.key`, `.env`, backups and every other hardened file are unchanged.
- **NGINX can now read the managed private key on hosts where the installing account is an ordinary administrator.** HTTPS installations failed with `nginx: [emerg] cannot load certificate key "/etc/nginx/certs/delta.key": ... Permission denied`, the key plainly present and non-empty on the host, and even container root refused — inside the container it showed as `---------- 0000`. Docker Desktop's WSL2 backend reaches a Windows drive over 9p, and the 9p server runs on the Windows side as the **logged-on user**, holding no ACL-bypass privilege; with `metadata` on that mount WSL derives every file's Linux mode from that account's *effective* Windows access. Measured on one host, one bind mount, one file per ACL: `SYSTEM:(F)` alone projects as `000`, `<user>:(R)` alone as `444`. So the key's `Administrators:(F) SYSTEM:(F)` hardening only ever worked while the account's token carried `BUILTIN\Administrators` **enabled** — true when signed in as the built-in Administrator with Admin Approval Mode off, which is the usual Windows Server posture and why Server 2022/2025 never showed this, and false for an ordinary administrator under UAC, where the unelevated token Docker Desktop runs with holds that group as deny-only and a deny-only SID can never grant access. `certs\delta.key` now additionally carries **Read** for the single account the installer is running as. Not Everyone, not Users, not Authenticated Users, and not write: the container must open the key and must never change it, and that is enforced by the host ACL itself rather than only by `:ro` on the mount. Everything else this installer hardens — `.env`, its backups, the key backups in `certs\` — is never opened by a container and keeps the narrower ACL unchanged. Re-running the installer repairs a key staged by an earlier version, and a certificate rollback re-applies the same entry.
- **A valid certificate and private key are no longer rejected with `sh: 1: set: Illegal option -`.** Every multi-line script this installer runs inside a container is a PowerShell here-string in a `.ps1` file, so its line endings are whatever git (`core.autocrlf`, and there is no `.gitattributes`), the last editor to touch the file, or `tools\build-release.ps1` left on disk. A carriage return is not whitespace to a POSIX shell — it is an ordinary character in the last word of the line — so a file carrying CRLF made the payload's first line `set -e<CR>`. Measured against `postgis/postgis:17-3.5`, whose `/bin/sh` is `dash` and which is the image this installer runs `openssl` in: `set` is a special builtin, so `dash` refuses the option, abandons the whole script and exits 2. Nothing reached stdout, so the comparison correctly reported that it could not compare anything — and quoted the single baffling line it had been given. Scripts are now normalised to LF at the one point they cross into a shell, so the outcome is impossible however the file reached the disk. **Nothing about the validation itself changed**: the key must still match the certificate, an encrypted key is still refused, and a Docker or OpenSSL failure is still a refusal rather than an acceptance.
- The same defect made self-signed HTTPS fail on the same machines, reported as `Generating a self-signed certificate failed: sh: 1: set: Illegal option -`. That payload was the more fragile of the two — its `openssl req` is spread over five lines with backslash continuations, so a CR was also what the backslash escaped — and it is fixed by the same normalisation. Reading the DELTA container's SMTP environment used a third multi-line payload with the same exposure, and is normalised too.
- The restart the installer needs part-way through is now asked for in a Windows dialog, **before** the machine goes down, rather than in a `Restart Windows now? [y/N]` line under half a screen of console text. **DELTA Setup - Windows Restart Required** offers OK and Cancel and states, while there is still somebody at the keyboard to read it, everything the operator would otherwise have had to discover afterwards: that Windows must restart, that work should be saved, that they must sign back in using the same Windows account, that setup then continues by itself, that this is **not** instant and waiting is the right response to an apparently idle screen, that `setup.ps1` must not be started again in the meantime, and that Windows may ask for administrator permission which has to be approved. OK arms the one-time RunOnce continuation and restarts; Cancel arms nothing, restarts nothing, keeps the reboot-required exit code and prints the manual commands. The dialog is raised on a TopMost owner window so it cannot open behind the installer's own console. Nothing else in the installer gained a dialog.
- **The post-restart "DELTA Setup - Continue Installation" confirmation is gone.** It asked a second time for a decision the operator had already made before the reboot, and it stood between the sign-in and the UAC prompt for no purpose. After signing in there is now no DELTA dialog at all: the continuation waits for the desktop shell, launches `setup.ps1` directly when the session is already elevated, and otherwise asks Windows for elevation — the UAC prompt is the only confirmation left after a restart. The resumed window says so and asks for patience rather than leaving a silent screen for up to ninety seconds. A declined or Windows-cancelled elevation still offers its single deliberate retry, at the console, and is still never automatic.
- If a dialog cannot be shown, the restart question falls back to exactly the console flow it had before — `Restart Windows now? [y/N]`, with the same explanation printed above it and the same typed-Y semantics, bare Enter still meaning no. A GUI failure must never be what stops an operator continuing. Two conditions are refused before anything is attempted, because they do not fail but hang: `MessageBox` blocks indefinitely on a non-STA thread rather than throwing (measured, not assumed), and a non-interactive session has nowhere to show a window. `-NonInteractive` is unchanged: no dialog, no question, no automatic restart, manual instructions and the reboot-required code.
- The generated continuation script is stripped of its comments before it is base64-encoded into the RunOnce value. Base64 of UTF-16 costs about 2.7 bytes of command line per byte of script against a 32767-character `CreateProcess` limit, and a long installation root can approach it on its own. Registration now refuses outright rather than writing a value Windows would not run. Comments are removed by the tokenizer and by exact character span, so a `#` inside a string literal is left alone.
- The resume after the prerequisite restart no longer dead-ends on Windows 11 when the elevation prompt does not come back approved. The continuation slept five seconds after logon and asked for elevation exactly once; RunOnce fires while the sign-in is still in progress, and an elevation requested before the desktop can host the consent UI is cancelled by Windows itself — reported as `The operation was canceled by the user`, the same message a declined prompt gives, with nothing having been shown to anybody. It now waits for the desktop shell of this logon session before asking, up to ninety seconds, and a refused elevation offers the prompt again rather than printing instructions and stopping. The retry is the operator's to ask for and never automatic, because Windows does not distinguish the two cancellations and an installer that re-prompts on its own after a `No` is an installer that gets clicked `No` again. Answering `n` stops, as does the elevation succeeding.
- A logon session that is already elevated — the built-in Administrator account, or a machine with UAC turned off — now runs the resumed installer directly instead of asking Windows to elevate something that is already elevated. There is one elevation flow in the installer and it is in the launcher: `setup.ps1` checks for Administrator and refuses without it, and deliberately does not elevate itself, so nothing can produce two prompts for one approval.
- The instructions printed when the automatic resume gives up are now instructions that work. They said `cd` and `.\setup.ps1`, which on a default Windows machine answers with `running scripts is disabled on this system` — so an operator following them exactly hit a second failure. They now name **Windows PowerShell as Administrator** explicitly and include `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`, with a note that it applies to that window only and changes nothing for the account or the machine. The installer's other "run it by hand" messages — the elevation refusal, and both restart-declined paths — now come from one shared helper and say the same thing, including `-InstallRoot` when the installation root is not `C:\DELTA`. No execution policy is written at any persistent scope, by any part of this installer, at any point.
- The restart prompt no longer promises that the resume is automatic or instant. It says the installer will try, that Windows has to finish signing in first, that a UAC prompt may have to be approved, and prints the manual commands alongside — a continuation that can be declined is not a guarantee, and describing it as one is how a working installer reads as a broken one.
- A host with no console window no longer loses the resume over a cosmetic window title.
- DELTA now comes back on its own after a Windows restart, and the startup task is actually registered. Where `com.docker.service` was present, the installer treated it as a boot-time mechanism that might start the engine, took that as covering the host, and registered nothing of its own — so a restarted machine had no DELTA startup task at all, Docker Desktop never started, and the stack stayed down. That service is Docker's privileged helper for a signed-in user; it starts neither Docker Desktop, nor the WSL2 VM, nor the Linux engine. It is now classified by what it does, no third-party mechanism can suppress DELTA's own task, and the task is registered unless this installation already owns a healthy, current one.
- The startup task now carries an at-logon trigger as well as its at-startup trigger, both running as the installing account with logon type S4U and no stored password. Docker Desktop's WSL2 engine is started by a per-user desktop application, so a trigger that fires before any session exists cannot be the only one: whichever trigger fires first performs the recovery, and the other finds the stack already up. The script it runs is unchanged in what it does — start Docker, wait for the Linux engine, check the database volume is still there, bring the Compose project up health-gated, confirm HTTP — and it is now passed `-FromStartupTask` so an unattended run can be told from a hand one.
- Windows-container mode is now reported as its own condition during an unattended start, instead of being folded into "the Docker engine did not become available". Nothing switches engines without being asked, at boot least of all.
- An installation that was left without a startup task — by the fault above, or because the task was removed since — now gets one back the first time the management screen is opened, the same way the NGINX rotation task is reconciled. It needs no Docker, changes nothing else, and rewrites nothing when the task is already correct.
- The management screen no longer reports `Restart  Configured` on a host with no startup task. That row came from `.delta-install.json`, which records what an installer did once and cannot know what is registered today. It is now measured against Task Scheduler on every refresh — the task must exist, be enabled, carry both triggers, and point at a script that is still on disk — and a mechanism that fails any of those is never reported as configured, whatever the record says. The row reads `Configured  automatic startup enabled` when the mechanism is in place and `Verified  automatic startup verified` once a real unattended recovery has happened; a recorded verification does not survive the task going away, and an unattended start that fails withdraws it.
- The Docker Desktop licensing disclosure is no longer shown twice. It used to be presented before the WSL platform was checked, so a host that needed WSL accepted the licence, installed WSL, was told to restart, and was asked to accept the same licence again on the way back. Backend prerequisites are now satisfied first, and the disclosure appears only when an installation is genuinely about to be attempted in that same run.
- Docker Desktop is no longer reported missing because the current PowerShell process cannot see it. "Docker Desktop is installed", "the `docker` command resolves here", "the engine is running" and "the engine is ready for Linux containers" are now measured as four separate facts: installation is read from the Windows registration (per machine *and* per user) and from Docker's own program directories, and the process PATH is repaired from the discovered install location before the CLI is judged absent. A stale PATH, a stopped engine, or an engine that is still starting can no longer trigger a second installation or a second licence prompt.
- An installation whose files are present but whose `docker.exe` cannot be found is now reported, with the three ways to resolve it, instead of being reinstalled over.
- A successful Docker Desktop installation no longer forces a restart unconditionally. The run continues to engine readiness when Docker's own installer did not ask for one, and stops cleanly for a restart when it did.

### Changed

- **The release artifact is now named after the repository.** It was `DELTA-windows-installer-docker-X.Y.Z.zip`; it is now `DELTA-windows-docker-installer-X.Y.Z.zip`, with `.zip.sha256` and the ZIP's top-level directory following it as they always have. The repository is `DELTA-windows-docker-installer` and the package never matched it — the two middle words were transposed. Nothing detected it because every consumer of the name agreed with every other one: `tools/build-release.ps1` minted it, and `release.yml`, `release.ps1`, the README and the release tests all pinned themselves to that, so the existing cross-checks passed while all five were wrong together. The tests now assert the package prefix against the repository name taken from the git remote, which is the check that was missing, and refuse the old spelling anywhere in the four files that build, publish, verify or document the artifact. **Anyone with automation that downloads the release asset by name must update it**: the download URL changes with the file name.
- The README's installation examples no longer extract to an invented `C:\Installers\DELTA`. They use `$HOME\Downloads\DELTA-windows-docker-installer-X.Y.Z` — the ZIP downloaded and extracted where Windows browsers normally put it, with `$HOME` rather than a made-up username — and say plainly that it is an example location and any local directory works. The TL;DR now also states the distinction the document only made later: the extracted **installer directory** holds `setup.ps1` and `bin\` and must be kept, and the **installation root** (`C:\DELTA` by default, unchanged) is a different directory that the installer creates for `.env`, the Compose file, the certificates and the data.
- The DELTA administrator password is now chosen explicitly during a new installation instead of being decided by an empty answer. The question was `Administrator password [Enter = generate]`, where generation was both the likeliest outcome and the easiest one to reach without meaning to — an operator who pressed Enter to get past a prompt they had not read found out at the end of the installation that they had chosen a credential. It is now asked as what it is: `1. Enter a password` / `2. Generate a strong password automatically`, with `Choose 1 or 2 [2]`. Enter still generates, so the fast path is unchanged; option 1 asks for the password twice, masked, and a mismatch is reported and asked again rather than accepted. Nothing else is taken as an answer — a password typed at the choice is refused as a choice, never accepted as the credential. The generator, its length, the point in the sequence at which the credential is applied, and the block that shows a generated password once at the end are all unchanged, as is the rule that a password the operator chose is never displayed. The database password prompt is untouched, and an installation whose administrator has already been secured is still never asked, so reruns, updates and restarts keep the credential somebody is already using.
- The database password is now chosen the same way the administrator credential is, instead of by an empty answer. `Database password [Enter = generate]` becomes `1. Enter a password` / `2. Generate a strong password automatically` with `Choose 1 or 2 [2]`, under a heading that says what the password is for and that the database is never published to the network. Enter still generates, so the fast path is unchanged; option 1 asks twice, masked, and a mismatch is reported and asked again rather than accepted. The generator, its length (32), the point at which the password is applied, and the rule that a cluster which already has one is never asked again are all unchanged, as is `-NonInteractive`, which still leaves `__GENERATE__` in `.env` for the stack stage to resolve. The two credentials now share one implementation of the question and one implementation of the masked double entry, so neither can drift from the other; the administrator wording, prompts, generated length and its "shown once at the end" promise are untouched.

- The Windows Server notice is now two sentences and a question: Docker does not officially support Docker Desktop on Windows Server, and DELTA has been successfully tested with it on Windows Server 2022 and 2025. Gone are the "this is a disclosure, not a refusal" / "the decision is yours" commentary — a `[y/N]` prompt already says that — and the echoed OS caption, which announced an evaluation build in the middle of a support notice that had nothing to do with it. Detection, the point at which it is asked, and the No default are unchanged.
- The Docker Desktop confirmation is now short and neutral: it states that Docker Desktop is required and will be installed, links Docker's licence terms, and asks `Continue with Docker Desktop installation? [y/N]`. The previous notice paraphrased Docker's subscription thresholds in the console; those are Docker's to state and Docker's to change, so the link is now the only authority quoted. The consent itself is unchanged — `--accept-license` still reaches Docker's installer only after an explicit `y`, Enter still means no, and the question still appears only when Docker Desktop is genuinely about to be installed.
- A new interactive installation now asks where to install rather than assuming `C:\DELTA` silently: `Use C:\DELTA as the installation directory? [Y/n]`. Enter accepts the default; declining opens a Windows folder-selection dialog — the same picker convention the certificate questions use, so no filesystem path is ever typed at a prompt. Cancelling the dialog returns to the question instead of cancelling the installation, and a directory that fails validation is refused with its reason and asked again.
- The chosen root is resolved before the prerequisite-restart continuation is registered, so an installation that restarts Windows part-way through resumes into the directory the operator chose.
- Unchanged in every other case: an explicit `-InstallRoot` is used without asking, `-NonInteractive` never opens a window, an existing installation keeps the root it is installed at, and a host that cannot show a dialog uses the default rather than asking a question it could not accept a second answer to.

## [1.0.0]

### Added

- First release of the Docker-based DELTA installer for Windows. `setup.ps1` is the single operator entry point: it chooses between installation and management from the installation state it detects on disk, rather than from a switch.
- Installation deploys DELTA as three containers — NGINX in front, the DELTA application, and PostgreSQL 17 with PostGIS — from a generated Compose project with pinned image digests.
- Docker Desktop is detected, and installed when absent, after its licensing terms are disclosed and accepted. Windows prerequisites, virtualization and the WSL2 backend are validated before anything is changed on the machine.
- Configuration is generated rather than hand-written: `.env`, the Compose file and the NGINX site configuration are produced from templates, with strong secrets generated for the database and the DELTA administrator account.
- HTTP and HTTPS ports are detected and conflicts resolved with the operator; the Windows firewall rules for the published ports are created.
- TLS supports three modes — plain HTTP, an operator-supplied certificate and key, or a generated self-signed certificate. A supplied key is verified to match its certificate before it reaches the live configuration.
- A management utility covering status, stack lifecycle, logs, database backup, in-place update, SMTP configuration, administrator credential reset, Domain Management and Certificate Management.
- Updates take a database backup first, verify the schema migration afterwards, and confirm the site answers over HTTP before reporting success.
- DELTA starts automatically after a Windows restart through a startup task that brings Docker and then the stack up, and NGINX access logs are rotated on a schedule.
- `uninstall.ps1` archives the database and the installation and verifies that archive before it is able to remove anything; there is no path that removes an installation without one.
